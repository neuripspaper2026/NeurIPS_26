# BFS-Bulk-Mach 规模修改实验报告

## 实验目的

验证对于固定规模的 benchmark，修改规模参数是否等同于"大量修改代码"。

## 实验设置

### 原始配置
```c
#define SCALE 8              // 2^8 = 256 nodes
#define EDGE_FACTOR 16       // 256 * 16 = 4096 edges
```

### 修改后配置
```c
#define SCALE 10             // 2^10 = 1024 nodes
#define EDGE_FACTOR 16       // 1024 * 16 = 16384 edges
```

### 预期影响
- 节点数: 256 → 1024 (4x)
- 边数: 4096 → 16384 (4x)
- 数据文件大小: ~4,612 行 → ~18,436 行 (4x)
- 计算复杂度: O(V+E) = O(4,352) → O(17,408) (4x)

---

## 实验过程

### Step 1: 修改宏定义 ✅
```bash
# 修改 bfs.h
sed -i 's/#define SCALE 8/#define SCALE 10/' bfs.h
```
**结果**: 修改成功

### Step 2: 重新编译 ✅
```bash
make clean
make all
```
**结果**: 编译成功，生成新的二进制文件

### Step 3: 测试旧数据兼容性 ❌
```bash
./EX1_optimized_codes/bfs_gcc input_data/mini/input/input.data input_data/mini/output/check.data
```
**结果**: 
```
Invalid input: line 512 of section
Success.
```
**分析**: 旧数据不兼容，需要重新生成

### Step 4: 重新生成数据 ⚠️

#### 4.1 首次尝试 - 栈溢出 ❌
```bash
make generate
```
**结果**: 
```
Segmentation fault (core dumped)
```

**原因分析**:
```c
// generate.c line 32
node_index_t adjmat[N_NODES][N_NODES];  // Stack allocation
```
- SCALE=8: `adjmat[256][256]` = 512 KB ✓
- SCALE=10: `adjmat[1024][1024]` = 8 MB ✗ (超过默认栈大小)

#### 4.2 增加栈大小 ✅
```bash
ulimit -s unlimited
make generate
```
**结果**: 成功生成新数据

#### 4.3 数据大小验证 ✅
```bash
wc -l input.data
# 18436 input.data  (正好是 4612 × 4)
```

### Step 5: 测试新数据 ❌
```bash
./EX1_optimized_codes/bfs_gcc input.data input.data
```
**结果**:
```
Invalid input: line 1 of section
Benchmark results are incorrect
```

**问题**: 数据解析失败，可能原因：
- 数值范围超出预期
- 格式不兼容
- 某些边界条件处理不当

## 关键发现

### 1. 修改规模的代价

修改一个简单的宏定义实际上影响了：
- ✗ 数据结构大小（静态数组）
- ✗ 内存使用模式（栈 vs 堆）
- ✗ 数据文件格式
- ✗ 所有编译产物
- ✗ 所有测试数据
- ✗ 可能的数值范围假设

### 2. 为什么固定规模 Benchmark 难以扩展？

```c
struct bench_args_t {
    node_t nodes[N_NODES];      // ← 编译时固定
    edge_t edges[N_EDGES];      // ← 编译时固定  
    level_t level[N_NODES];     // ← 编译时固定
    // ...
};
```

**影响**:
- 所有使用这个结构的代码都需要重新编译
- 无法动态改变规模
- 数据文件必须匹配编译时的规模

### 3. 连锁反应

```
修改 SCALE
  ↓
N_NODES, N_EDGES 改变
  ↓
数组大小改变
  ↓
内存布局改变
  ↓
可能触发栈溢出/性能问题
  ↓
数据格式需要调整
  ↓
所有数据需要重新生成
  ↓
可能引入新的 bug
```

## 对比：修改规模 vs 改变模式

| 方面 | 修改规模 (SCALE 8→10) | 改变模式 (不同随机种子) |
|------|---------------------|----------------------|
| **修改源码** | ✗ 需要 | ✓ 不需要 |
| **重新编译** | ✗ 必须 | ✓ 不需要 |
| **重新生成数据** | ✗ 必须全部重新生成 | ✓ 一次性生成多个模式 |
| **技术问题** | ✗ 栈溢出、数值溢出 | ✓ 无 |
| **兼容性** | ✗ 破坏所有旧数据 | ✓ 保持兼容 |
| **调试难度** | ✗ 高 | ✓ 低 |
| **优化变体** | ✗ 需要同步修改 | ✓ 无需修改 |
| **数据一致性** | ✗ 失去可比性 | ✓ 保持一致 |
| **测试多样性** | ✓ 不同规模 | ✓ 不同拓扑 |
| **实现成本** | ✗ 高 | ✓ 低 |

## 结论

### ✅ 实验验证了核心假设

**"修改 size 就相当于大量修改原始代码" - 完全正确！**

即使只修改一个宏定义，实际上需要：
1. 修改源文件（1 处）
2. 重新编译所有代码（至少 4 个文件）
3. 调整系统配置（栈大小）
4. 重新生成所有数据（5 个 size × 2 文件）
5. 可能需要调试新的问题
6. 所有优化变体代码也需要同步修改

### 🎯 最佳实践

对于固定规模的 benchmark（如 BFS-bulk-mach），推荐：

1. **保持原始规模不变**
   - 避免破坏代码兼容性
   - 避免引入新的技术问题

2. **使用不同数据模式**
   - 不同随机种子 → 不同图拓扑
   - 测试算法在不同输入下的正确性
   - 保持代码和数据的一致性

3. **清楚说明限制**
   - 在 README 中明确标注是固定规模
   - 解释为什么使用不同模式而非不同规模

### 📝 经验教训

1. **固定规模不是设计缺陷**
   - 某些算法本身就有标准规模（如 AES 128位）
   - 固定规模可以简化实现和优化

2. **扩展性的代价**
   - 动态规模需要动态内存分配
   - 可能影响性能和可优化性
   - 增加代码复杂度

3. **数据集设计的智慧**
   - "不同模式"是固定规模 benchmark 的优雅解决方案
   - 在不修改代码的前提下提供测试多样性
   - 保持了简单性和一致性的平衡
